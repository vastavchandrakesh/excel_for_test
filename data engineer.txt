1. Retry with exponential backoff (API ingestion)

import time, random, functools

def retry(max_attempts=5, base=1.0, exceptions=(Exception,)):
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(*a, **kw):
            for attempt in range(1, max_attempts + 1):
                try:
                    return fn(*a, **kw)
                except exceptions:
                    if attempt == max_attempts:
                        raise
                    time.sleep(base * 2 ** (attempt - 1) + random.random())
        return wrapper
    return deco

Say: jitter avoids thundering herd; retry only transient errors (429, 5xx, timeouts), never 4xx like 400 or 403.

2. Chunking with overlap

def chunk(text, size=500, overlap=50):
    if overlap >= size:
        raise ValueError("overlap must be < size")
    words, step = text.split(), size - overlap
    return [" ".join(words[i:i + size])
            for i in range(0, max(len(words) - overlap, 1), step)]

Say: in production chunk by tokens or document structure (headings, paragraphs), not raw words.

3. Idempotent ingestion (skip unchanged documents)

import hashlib, boto3
s3 = boto3.client("s3")

def doc_hash(bucket, key):
    body = s3.get_object(Bucket=bucket, Key=key)["Body"].read()
    return hashlib.sha256(body).hexdigest()

def needs_reindex(bucket, key, index_state: dict):
    h = doc_hash(bucket, key)
    if index_state.get(key) == h:
        return False
    index_state[key] = h   # in real life: persist in DynamoDB or S3
    return True

4. Cosine similarity top-k (explains what a vector DB does)

import numpy as np

def top_k(query_vec, matrix, k=5):
    q = query_vec / np.linalg.norm(query_vec)
    m = matrix / np.linalg.norm(matrix, axis=1, keepdims=True)
    scores = m @ q
    idx = np.argpartition(-scores, k)[:k]
    return idx[np.argsort(-scores[idx])], scores[idx]

5. Flatten nested JSON from an API

def flatten(d, parent="", sep="."):
    out = {}
    for k, v in d.items():
        key = f"{parent}{sep}{k}" if parent else k
        if isinstance(v, dict):
            out.update(flatten(v, key, sep))
        else:
            out[key] = v
    return out

6. Pagination with a generator and a watermark

import requests

def fetch_since(url, headers, since):
    page = 1
    while True:
        r = requests.get(url, headers=headers, timeout=30,
                         params={"page": page, "updated_after": since})
        r.raise_for_status()
        items = r.json().get("items", [])
        if not items:
            return
        yield from items
        page += 1

Say: the generator keeps memory flat; store the max updated_at as the next watermark only after a successful write.

B. RAG AND GENAI
----------------------------------------------------------------

1. Walk me through your RAG architecture.
"Ingestion: documents land in S3, get text-extracted (Textract for scanned files and diagrams), cleaned, chunked, embedded through Bedrock, and indexed with metadata like source and version. Query: the request comes through API Gateway to Lambda, which embeds the question, retrieves the top-k chunks, and builds a prompt that tells Claude to answer only from the context and cite sources. The response goes back to the React UI with citations. I designed the retrieval pipeline and the Lambda orchestration. Monitoring is latency, token usage and user feedback, and the data layer stays fresh through incremental re-ingestion."

2. Which vector store and embedding model, and why?
"I used Amazon Titan Text Embeddings v2* with OpenSearch Serverless*, because it is managed and AWS-native, and right-sized for a small corpus in a POC*. For production scale I'd move to OpenSearch Serverless or Aurora pgvector for metadata filtering, hybrid search and horizontal scale."
(If your POC used a simple index, say so. "Right-sized for the corpus, here's the scale path" is a strong answer.)

3. How did you choose chunk size and overlap?
"I started from document structure (headings and paragraphs), the embedding model's token limit, and the granularity of answers users needed. I used roughly 500* tokens with 50* overlap, then tested against real questions and adjusted. Too small loses context, too large dilutes relevance and burns tokens."

4. How do you improve retrieval quality?
"I build an evaluation set of real questions with expected source chunks first, so every change is measured. Then, in order of payoff: fix parsing and chunking, add hybrid search, add metadata filters, add a reranker, and rewrite queries. I change one thing at a time and track recall@k."

5. Hybrid vs semantic-only search?
"Vector search finds meaning, so it handles paraphrases. Keyword search (BM25) finds exact tokens like error codes, service names and acronyms, which embeddings blur. Architecture reviews are full of exact service names, so hybrid fits. I combine scores with reciprocal rank fusion or a reranker."

6. How do you reduce hallucinations?
"Five layers: retrieve good context, instruct the model to answer only from it, require citations, give it a refusal path ('I don't know') when retrieval is weak, and keep temperature low. In regulated settings I'd add Bedrock Guardrails contextual grounding checks. In my work I used grounding in retrieved context and source citations, plus a refusal path*."

7. How do you evaluate a RAG system?
"Retrieval and generation are evaluated separately. Retrieval: recall@k and context precision against a golden set. Generation: faithfulness (is every claim supported by context) and answer relevance, scored by LLM-as-judge and spot-checked by humans. Online: thumbs up/down, unanswered rate and escalations. My evaluation so far has been a small set of real questions I checked manually, with spot checks on citations*, and the next step is a fixed regression set that runs before each prompt or retrieval change."

8. How do you keep the index fresh?
"Event-triggered ingestion: an S3 event starts the pipeline. I hash document content to skip unchanged files, use deterministic chunk IDs (doc#chunk_n) so upserts are idempotent, and delete orphaned chunks when a document shrinks or is removed. A scheduled full reconciliation catches missed events."

9. How do you enforce document-level access in RAG?
"Store an access attribute (group, classification) as metadata on every chunk, then apply a filter at retrieval time based on the caller's identity from the token. The filter must apply before the LLM sees anything, because you can't un-leak text from a prompt. I'd also log retrievals for audit. This is the same least-privilege thinking as my Unity Catalog work."

10. Prompt injection defenses?
"Treat retrieved text and user input as untrusted data. Keep instructions in the system prompt, wrap retrieved content in delimiters and tell the model it's data, not instructions. Add input and output guardrails, give the app no tools or permissions it doesn't need, and validate structured outputs. For agents, require confirmation before any write action."

11. Bedrock Knowledge Bases vs custom pipeline?
"Knowledge Bases for speed: managed ingestion, chunking, sync, and it supports metadata filtering and reranking. Custom when I need control over parsing (tables, diagrams), hybrid scoring, custom access control, or unusual sources. For a POC I'd start managed and go custom where it hurts."

12. How does Textract handle architecture diagrams?
"Textract extracts text and labels, not relationships between components. So I passed the image to Claude 3's vision capability alongside the extracted text*. Inferred relationships can be wrong, so the output is positioned as an expert-assist with a human sign-off, not a final audit."

13. How do you get reliable structured output?
"Put the exact JSON schema in the prompt with an example, set low temperature, validate the response against the schema in code, and retry with the error message on a parse failure. On Bedrock, tool-use or structured-output features can enforce a schema more strictly."

14. How do you control GenAI cost?
"Trim context (fewer, better chunks), cache frequent questions, route simple queries to a smaller model, cap output tokens, and track cost per query in CloudWatch. My Architecture Reviewer cost came to a few dollars in AWS usage* versus manual review, which is where the 70% saving came from."

15. When would you use agents or multi-agent systems?
"Only when the path isn't known in advance: the model needs to choose among tools or steps. If the workflow is deterministic, plain RAG or Step Functions is cheaper, faster and more predictable. Agents need step limits, timeouts, fallbacks and tracing. I haven't run a multi-agent system in production. I understand supervisor/worker patterns and Bedrock Agents with action groups, and I'd start with one agent and add more only when a single one fails."

16. Bedrock vs SageMaker?
"Bedrock for managed foundation models behind an API, with no infrastructure to run. SageMaker when I need custom training, fine-tuning on proprietary data, a model Bedrock doesn't offer, or control over hosting. I've used Bedrock in production. SageMaker I know conceptually, and my data pipeline skills feed its training jobs."

17. Guardrails for a regulated domain?
"Bedrock Guardrails for PII redaction, denied topics and content filters, applied to both input and output. Around that: private connectivity (VPC endpoints), least-privilege IAM, encryption, audit logging of prompts and responses with PII controls, document-level access, and a human review path for high-risk answers. My Pfizer work on masking, audit logging and Unity Catalog is the same discipline."

18. How would you monitor a GenAI app in production?
"Operational: latency (p50/p95), error and throttle rates, token usage and cost per query. Quality: feedback rate, unanswered rate, retrieval-hit rate, and sampled faithfulness scoring. Dashboards and alarms in CloudWatch, with invocation logging enabled. Alerts on cost spikes and quality drops."

19. What do you do when the model is slow or throttled?
"Retries with exponential backoff and jitter, streaming so users see tokens early, async processing for long jobs, a request quota increase, a cross-region inference profile or fallback model, and caching. At the API layer, respect the gateway timeout by going async or streaming."

D. SPARK AND DATA ENGINEERING
----------------------------------------------------------------

30. Data skew and fixes?
"Skew means a few keys hold most rows, so a few tasks run far longer. Spot it in the Spark UI as one slow task and uneven shuffle sizes. Fixes: enable AQE skew join, broadcast the small side, salt the hot key, or filter and handle null keys separately."

31. Narrow vs wide transformations?
"Narrow (map, filter) work within a partition with no shuffle. Wide (groupBy, join, distinct, repartition) move data across the network and create stage boundaries. Wide operations are where you optimize."

32. repartition vs coalesce?
"repartition does a full shuffle and balances partitions, and can increase or decrease the count. coalesce only reduces partitions and avoids a full shuffle but can leave them uneven. I use coalesce to cut output file counts, and repartition when I need balance or key-based layout."

33. Small files problem?
"Many tiny files make slow listing and many tasks. Fix at write time by controlling partition count (coalesce/repartition) or using maxRecordsPerFile, and afterward by compaction, such as Delta OPTIMIZE or a periodic compaction job. Avoid over-partitioning, like partitioning by a high-cardinality column."

34. How does AQE help?
"It re-optimizes at runtime using real statistics: coalesces small shuffle partitions, switches a sort-merge join to broadcast when one side turns out small, and splits skewed partitions. It was part of my 40% shuffle reduction, along with partition pruning and broadcast joins."

35. Delta Lake features?
"ACID transactions, schema enforcement and evolution, time travel, MERGE for upserts and SCD, OPTIMIZE with Z-order for file compaction and data skipping, and VACUUM for cleanup. I used schema enforcement and time travel in the medallion layers at Pfizer."

36. Designing idempotent pipelines?
"A rerun must produce the same result. Techniques: deterministic keys, MERGE instead of append, overwrite by partition, run-date parameters instead of 'now', and writing to a staging location before an atomic swap. That's why failures at McDonald's could be rerun without duplicates."

37. Incremental load design?
"Track a watermark (max updated_at or an ID) and load only newer rows, committing the watermark only after a successful write. Handle late-arriving data with a lookback window, capture deletes through CDC or soft-delete flags, and reconcile counts periodically."

38. Data quality approach?
"Checks at each layer boundary: schema and nulls at Bronze->Silver, duplicates and referential integrity at Silver->Gold, plus row-count reconciliation to source. Bad records go to a quarantine table instead of failing the whole run, and failures alert the team. My Snowflake validation covered null checks, duplicates, row counts and schema validation."

39. SCD Type 2?
"Keep history by closing the current row (is_current = false, set end_date) when tracked attributes change, then inserting a new current row with a new start date. In Snowflake or Delta this is a MERGE plus an insert of the new version. Use a surrogate key so facts join to the correct version."

40. Dimensional modeling decisions?
"Declare the grain first, then choose dimensions and measures. Use conformed dimensions so different facts join consistently, surrogate keys to insulate from source key changes, and the right SCD type per attribute. I applied this across 10+ source systems at McDonald's."

E. SQL

41. Second-highest per group:
DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC), filter = 2. Dense rank is used so ties don't skip the rank.

42. Running totals and moving averages:
SUM(x) OVER (ORDER BY dt ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW). A 7-day average uses ROWS BETWEEN 6 PRECEDING AND CURRENT ROW. Mention ROWS vs RANGE when dates have gaps or ties.

43. Gaps and islands:
Take login_date - ROW_NUMBER() OVER (PARTITION BY user ORDER BY login_date) as a group key. Consecutive dates share the same key, so group by it and take MIN/MAX. De-duplicate dates first.

44. Dedup keeping the latest:
ROW_NUMBER() OVER (PARTITION BY business_key ORDER BY updated_at DESC) in a CTE, keep rn = 1. Add a uniqueness check afterward. This is your real dedup-CTE fix.

45. Customers with no orders:
LEFT JOIN orders ... WHERE o.customer_id IS NULL, or NOT EXISTS. Avoid NOT IN when the subquery can return NULLs.

46. ROW_NUMBER vs RANK vs DENSE_RANK:
ROW_NUMBER gives unique sequential numbers even for ties. RANK gives ties the same number and skips the next ones (1,1,3). DENSE_RANK gives ties the same number without skipping (1,1,2).

47. Query optimization:
Read the execution plan for scans, joins and spills. Filter early, select only needed columns, avoid functions on filter columns (they block partition pruning and index use), partition and cluster on common filters, pre-aggregate heavy joins, and check join order and skew. My 35% report runtime cut came from a star schema, pre-aggregation layers, CTE and window-function tuning, and partition pruning*.
